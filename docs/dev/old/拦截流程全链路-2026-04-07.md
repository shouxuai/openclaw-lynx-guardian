## 一、Hook 执行顺序总览

```
用户发送消息
    │
    ▼
[1] message_received
    │
    ▼
[2] before_agent_start
    │
    ├─── LLM 开始执行（若未被拦截）
    │         │
    │         ▼ (每次工具调用)
    │    [3] before_tool_call
    │         │
    │         ▼ (LLM stream 完成)
    ▼
[4] agent_end
    │
    ▼
[5] before_message_write
```

## 二、[1] message_received 详细流程

```
message_received(event, ctx)
    │
    ├─► 读取 sessionKey / channelId / confirmationPhrase
    │
    ├─► [A] 确认口令检测
    │       isConfirmationPhrase(text, phrase)
    │       命中 → approvePendingOverride() → 标记放行 → 返回
    │
    ├─► [B] SensitiveDataBlocker.containsSensitiveData(text)
    │       检测步骤（顺序执行，命中即返回 true）：
    │         1. blockedTerms 关键词匹配（lowercase includes）
    │            "private key / secret token / bearer token / oauth token /
    │             jwt token / credential / api key / access token"
    │         2. highConfidencePatterns 正则
    │            openai_key / github_token / aws_access_key / jwt_token /
    │            slack_token / stripe_key / google_api / private_key
    │         3. genericPatterns 正则
    │            api_key_assignment / hex_key(41+位) / base64_key(40+位)
    │         4. isHighEntropy() 熵检测
    │            匹配 /[A-Za-z0-9_\-]{32,}/g，entropy > 5.0 即命中
    │       命中 → block: true，直接返回，不进入后续流程
    │
    └─► [C] guardInput(text, sessionKey, guardContext)
            → 见【赋分引擎】章节
            L3/L4 → block
            L2 → warn（不 block，加 warning 字段）
            L1 → log only
            L0 → allow
```

## 三、[2] before_agent_start 详细流程

```
before_agent_start(event, ctx)
    │
    ├─► baseIpInfo() → 公网暴露检查（checkPublicAccess API）
    │       is_public = true → prependContext 加警告
    │
    ├─► extractContentAfterDate(promptText) → userInput
    │       去掉 "[日期时间]" 前缀；Feishu 会有 "发送者: " 前缀，
    │       isManualDiscoveryRequest 会自动识别 "名字: /command" 格式
    │
    ├─► isManualDiscoveryRequest(userInput)
    │       精确匹配：check / /check / lynx-check / /lynx-check / openclaw-check / /openclaw-check
    │       也匹配 "发送者: /命令" 格式（取 ": " 后的内容再匹配）
    │       模糊匹配：同时含 actionKeywords + targetKeywords + signalKeywords
    │       命中 → buildManualLynxCheckReport() → 写入 DISCOVERY_RESULT_PATH
    │             → prependContext 注入系统指令（含渠道判断）
    │               webchat → 告知用户"请刷新查看"
    │               其他 → 告知用户"报告将自动附在回复末尾"
    │
    ├─► checkContent(userId, input, type=1) API  ← 后端内容检查（输入侧）
    │       返回 { risk_level: 0|1, is_safe, level_one/two/three }
    │       注意：content check 只返回 0 或 1，不返回 2/3
    │       risk_level >= 3 → buildApiRiskAssessment() → resolveRiskPolicy()
    │                         → block（或 block+确认口令）
    │       risk_level 1/2  → 仅追加 warning 到 prependContext，不阻断
    │
    ├─► guardInput(promptText, sessionKey, guardContext)
    │       → 见【赋分引擎】章节
    │       L3/L4 → block（或 block+确认口令，取决于 resolveRiskPolicy）
    │
    └─► token optimizer
            recommendContext() / routeModel() / checkBudget()
            → 注入上下文优化提示到 prependContext
```

## 四、[3] before_tool_call 详细流程

```
before_tool_call(event, ctx)
    │
    ├─► consumeApprovedOverrideFull() → 检查是否已有授权，有则跳过后续拦截
    │
    ├─► getWorkflowAuth() → 工作流授权窗口检查
    │       在授权窗口内 → 记录审计日志 → 直接放行
    │
    ├─► [A] Skill Guard（仅当 toolName 匹配安装模式时）
    │       detectSkillInstall(toolName, params)
    │       命中 → assessSkillRisk() → quickBlacklistCheck()
    │             critical/malicious → block
    │             warning → 记录，不 block
    │
    ├─► [B] 本地黑名单检查
    │       exec 命令 → checkExecBlacklist(command)
    │           Phase 1：全命令字符串检查 PIPE_ATTACKS + CHAIN_ATTACKS
    │           Phase 2：splitCommand() 按 shell 操作符分段
    │               每段：
    │                 1. CRITICAL_OVERRIDE（不受 SAFE_EXEC 白名单保护）
    │                    - cat/less/more/head/tail /etc/passwd|shadow|sudoers
    │                    - /etc/shadow（路径兜底）
    │                 2. SAFE_EXEC 白名单匹配 → 跳过该段
    │                 3. CRITICAL_EXEC → 返回 critical
    │                 4. WARNING_EXEC → 返回 warning
    │       write/edit 路径 → checkPathBlacklist(filePath)
    │           CRITICAL_PATH → critical
    │           WARNING_PATH → warning
    │       未命中 → return（不继续）
    │
    ├─► [C] 命中黑名单后：调用 checkTool(userId, content) API  ← 后端工具检查
    │       返回 { risk_level: 0|3 }
    │       注意：tool check 只返回 0 或 3，不返回 1/2
    │       risk_level >= 2 && !approvedToolOverride
    │           → buildApiRiskAssessment(risk_level) → resolveRiskPolicy()
    │           → block + 确认口令（若 override allowed）
    │       risk_level >= 3 && approvedToolOverride（override 已消费）
    │           → 硬拦截（无口令）
    │       risk_level < 2 → 仅 log，不 block
    │
    └─► [D] guardToolCall(toolName, params, sessionKey, guardContext)
            → 见【赋分引擎】章节
            L3/L4 → block
```

## 五、[4] agent_end 详细流程

```
agent_end(event, ctx)
    │
    ├─► revokeWorkflowAuth() → 回收工作流授权窗口
    │       有授权记录 → 格式化审计摘要
    │       ctx.sendMessage 存在时尝试发送（实测 webchat/feishu 均无 sendMessage）
    │
    ├─► Discovery 报告兜底（实际无效，sendMessage 不可用）
    │
    ├─► guardOutput(output)  ← 输出侧安全检测
    │       detectSystemPromptLeak(output)
    │         检测 SOUL/TOOLS/SHIELD/SKILL/AGENTS/MEMORY.md 及内部实现名泄露
    │         high → L4, score=6+; low → L3, score=3
    │       命中 → redactAgentOutput(event, replacement)
    │               event.output = replacement（实测 event.output=undefined，无效）
    │               event.messages 末尾 text 替换（best-effort，效果待定）
    │             → pushRecord(2)
    │
    └─► checkContent(userId, output, type=2) API  ← 后端内容检查（输出侧）
            返回 { risk_level: 0|1 }
            risk_level > 0 → 仅打日志，无任何阻断动作（纯观测）
```

## 七、赋分引擎（guardInput / guardToolCall）

### 7.1 五维度评分

```
ScoreDimensions {
    intentClarity:      0-2  （0=良性，1=模糊，2=恶意）
    potentialHarm:      0-2  （0=无害，1=轻度，2=严重）
    reversibility:      0-2  （0=可逆，1=部分，2=不可逆）
    authorizationStatus:0-2  （0=已授权，1=不确定，2=未授权）
    patternMatch:       0-2  （0=未命中，1=弱匹配，2=强匹配）
}

computeRiskScore() = sum(5 dimensions)  →  范围 0-10
```

各维度使用 `Math.max()` 更新，同一维度多个模块触发**不叠加**，取最高值。

### 7.2 模块触发规则

| 模块 | 维度设置 | forcedMinLevel |
|------|----------|----------------|
| M0: identity_verification | directOwnerClaim: clarity=2,auth=2,pattern=2; relationClaim: 各=1 | L2 |
| M1: prompt_injection | confidence≥0.7: pattern=2; ≥0.6: clarity=2; harm=2; rev=1; auth=1 | confidence≥0.85 或 indirect → L4，否则 L3 |
| M2: system_prompt_extraction | clarity=2,harm=2,rev=1,auth=2,pattern=2 | L4 |
| M2: protected_file_access | op=unknown: clarity=1; op=write: rev=2; op=read: rev=1; harm=2,auth=2,pattern=2 | L4 |
| M3: over_agency | selfModify: clarity=2,harm=2,rev=2,auth=2; else: 较低 | selfModify → L4；else → L3 |
| M5: credential_theft | primarySecrets(env/ssh/aws/gnupg/etc_passwd等): L4；其他: L3 | 见左 |
| M6: malicious_code | 全部满 2；legalContext 时 auth=1 | legalContext+dualUse → L3；else → L4 |

### 7.3 forcedMinLevel 与 applyMinimumLevel

```
minScoreForLevel:
    L0 → 0
    L1 → 1
    L2 → 4
    L3 → 7
    L4 → 9

applyMinimumLevel(score, minLevel) = Math.max(score, minScoreForLevel(minLevel))

最终 score = Math.min(applyMinimumLevel(rawScore + anomalyAdj, forcedMinLevel), 10)
```

### 7.4 异常会话调整（computeAnomalyAdjustment）

仅当本次有模块触发时才计算（`triggeredModules.length > 0`）：

```
+2  最近3轮分数连续递增 且 总增幅 >= 4（渐进攻击检测）
+1  本次同时触发 >= 2 个模块
+1  同一模块在会话内被拒绝次数 >= 3（重复绕过尝试）
    豁免模块（不计入次数）: M0:identity_verification / M2:protected_file_access / M3:over_agency
```

verifiedOwner 时：`score = Math.max(0, score - 2)`（最后应用）

### 7.5 评分 → 等级 → 动作

```
scoreToLevel:
    0     → L0 → allow
    1-3   → L1 → log
    4-6   → L2 → warn
    7-8   → L3 → block
    9-10  → L4 → deny
```

## 八、resolveRiskPolicy（放行策略）

```
resolveRiskPolicy(assessment, config)
    │
    ├─► areAllModulesOverridable(modules, config)
    │       检查每个模块是否在 MODULE_OVERRIDE_ELIGIBLE 中为 true
    │       M0:identity_verification  → true
    │       M2:protected_file_access  → true（可配置关闭）
    │       M3:over_agency            → true（需 moduleOverrides.M3.allowOneTimeOverride=true）
    │       M1/M2:extraction/M5/M6/fatal_triangle → false（硬拒绝）
    │       有任意 false → finalAction=deny，不提供口令
    │
    └─► 全部 overridable
            检查 assessment.level 是否在 allowOneTimeOverrideLevels 内（默认 L2/L3/L4）
            在内 → override.allowed=true，提供 confirmationPhrase
            不在内 → override.allowed=false
```

## 九、buildApiRiskAssessment（后端结果转换）

```
后端 risk_level → RiskAssessment:
    >= 3  → level=L4, score=9, action=deny     （tool check 实际只返回 0/3）
    == 2  → level=L2, score=6, action=block    （当前后端从不返回 2，死路）
    == 1  → level=L1, score=3, action=warn     （content check 返回 0/1）
    == 0  → level=L0, score=0, action=allow
```

**注意**：后端 API 实际返回值：
- `checkContent`（内容检查）：只返回 **0 或 1**
- `checkTool`（工具检查）：只返回 **0 或 3**
- risk_level=2 的分支在当前后端实现中永远不会触发
